# 디스크에 사는 51B

> 원본(그래프·서식 포함): https://claude.ai/code/artifact/a8103a76-e720-4770-b550-9832fd5c9a2b
>
> 이 마크다운은 아카이브용 변환본이다. **인라인 SVG 그래프는 빠져 있고** 캡션만 남았다.
Qwen3.8-Flash-Next · llama.cpp · CMP 170HX


177B 모델의 파라미터 중 **51.2B**가 VRAM 에도 RAM 에도 올라가지 않는다. NVMe 위의 파일에 그대로 누워 있고, 토큰당 **약 1.9 KB**씩만 깨어난다. 그런데 그렇게 해도 **속도가 거의 안 떨어진다** — 왜 그런지가 이 글이다.
- 47.9 tok/s — 테이블이 캐시에
- 41.9 tok/s — 캐시 전무 (바닥)
- 44.9 GiB — VRAM / 64.0
- 2.7 MB/s — SSD 읽기
- 0 B — SSD 쓰기

## 01. 무슨 일이 일어나는가

모델 파일을 열어두고, 텐서 하나를 *메모리로 읽어들이지 않은 채* 남겨둔다.
보통 모델을 올린다는 건 파일을 읽어 그 내용을 메모리에 **복사**하는 일이다. 여기서는 그 복사를 하지 않는다. 파일을 주소 공간에 붙여만 두고(`mmap`), 내용은 계속 디스크에 둔다. 연산이 그 주소를 건드리는 순간 커널이 **4 KB 한 장만** 읽어 온다.
llama.cpp 에 이 용도의 전용 경로가 있다. 아키텍처가 텐서에 `TENSOR_READ_LAZY` 를 달면 로더가 그것만 mmap 영역에 남긴다. 스위치는 `--lazy-mode`, 기본값 `auto` 가 **4 GiB 를 넘는 마킹된 텐서**를 자동으로 잡는다. 36 GiB 짜리 n-gram 테이블은 당연히 걸린다.
> **[그림 — 원문 HTML 참조]** **왕복 경로.** 붉은 선이 디스크를 건드리는 유일한 구간이다. 캐시가 버려져도 원본이 파일에 그대로 있으므로 **쓰기가 발생하지 않는다** — 이것이 스왑과의 결정적 차이이고, SSD 수명을 걱정하지 않아도 되는 이유다.

**흔히 말하는 오프로딩과도 다르다.** 오프로딩은 가중치를 호스트에 두었다가 필요할 때 GPU 로 실어 나른다. 여기서는 테이블을 GPU 로 보내지 않는다. 연산 자체를 CPU 에서 하고 **결과만** 건네준다 — 토큰당 약 5 KB 다.

## 02. 왜 이게 되는가

저장장치가 빨라서가 아니라, *이 텐서가 행렬곱에 안 쓰이기 때문*이다.
토큰 하나를 만들려면 그 토큰에 관여하는 가중치를 전부 한 번씩 읽어야 한다. 그래서 어떤 가중치를 느린 저장 계층에 둬도 되는지는 **토큰당 몇 바이트를 읽는가** 하나로 갈린다.

### 전문가 가중치는 이 문제를 풀지 못한다

이 모델의 본체는 125B 중 토큰당 6B 만 활성화된다. 여기서 흔한 오해가 나온다 — *그럼 6B 만 갖고 있으면 되지 않나?* 아니다. **어느** 전문가 10개가 켜질지는 라우터가 그 토큰의 내용을 보고 정하고, 매 토큰 달라진다. 미리 알 수 없으니 512개 전부가 즉시 읽힐 수 있는 곳에 있어야 한다.
> **[그림 — 원문 HTML 참조]** **같은 "희소 접근"인데 성질이 정반대다.** 왼쪽은 어느 조각이 필요한지를 **학습된 라우터가 그 자리에서 정하고** 조각 하나가 수백 MB 다. 오른쪽은 주소가 직전 토큰들의 순수 함수이고 조각 하나가 120 바이트다. 성패를 가르는 건 희소성이 아니라 **주소의 예측 가능성 × 조각의 크기**다.

llama.cpp 의 정의에서 이 텐서의 연산은 행렬곱이 아니라 `GET_ROWS`, 즉 **색인**이다. 가중치가 아니라 **사전**인 셈이고, 사전은 통째로 펼쳐 둘 필요가 없다. 36 GiB 중 토큰당 1.9 KB — **1,300만 분의 1**이다.

## 03. 중요한 건 장치 종류가 아니다

"읽기 한 번에 얼마나 걸리나" *하나*가 전부다. 그걸 실험으로 확인했다.
토큰 하나를 만드는 데 이 박스에서 **20.6 ms** 가 걸린다. 그중 GPU 가 하는 일이 대부분이고, 디스크는 **캐시가 하나도 없는 최악의 조건에서조차** 이만큼이다:
| 토큰 하나 · NVMe · 최악 조건 | 시간 | 비중 |
|---|---|---|
| GPU 연산 | 20.6 ms | 86% |
| 디스크 — 4 KB 읽기 16회 | 3.3 ms | 14% |
| 합 | 24.0 ms | = 41.9 tok/s |

그러면 **디스크가 얼마나 느려지면** 이 비중이 뒤집힐까. GPU 연산 20.6 ms 를 디스크가 따라잡으려면 읽기 16회로 그만큼을 써야 하니 **한 번에 1.29 ms** 다. 그게 임계다. NVMe 는 209 µs 로 임계의 **6분의 1**이다.

### 그래서 SSD 를 일부러 느리게 만들어 봤다

장치를 바꾸는 대신 **같은 NVMe 에 경쟁 읽기 부하를 걸어** 읽기 한 번의 시간만 올렸다. 하드디스크가 느린 이유(헤드가 움직여야 함)와는 전혀 다른 원인인데, **결과가 같은지**를 보는 것이다.
| 조건 | 읽기 1회 | 캐시 있을 때 | 캐시 없을 때 |
|---|---|---|---|
| NVMe · 부하 없음 | 259 µs | 48.5 | 42.1 |
| NVMe · 경합 | 1,183 µs | 48.5 | 32.2 |
| NVMe · 경합 | 4,462 µs | 48.4 | 13.6 |
| NVMe · 경합 (최대) | 6,824 µs | 48.3 | 10.0 |
| HDD · 2009년 7200 rpm | 7,237 µs | 48.8 | 9.3 |

> **느리게 만든 SSD 와 진짜 하드디스크가 같은 값을 낸다.** 읽기 시간이 1.06배 차이일 때 속도도 1.08배 차이다 — **같은 곡선 위에 있다.** 즉 하드디스크가 느린 이유가 "회전 디스크라서" 가 아니라 **"읽기 한 번에 7 ms 가 걸려서"** 다. 장치 종류는 그 숫자를 통해서만 영향을 준다.

**그리고 오른쪽 두 열의 대비가 이 방식의 성질이다.** 읽기 시간이 26배 벌어지는 동안 **"캐시 있을 때" 열은 48.3~48.8 로 꿈쩍도 하지 않는다.** 디스크는 **읽으러 갈 때만** 존재한다. 실제 운용은 두 열 사이 어딘가고, 이 박스에서 관측된 미스율은 **35~100%** 였다 — 남는 RAM 이 자동으로 캐시가 되므로 캐시가 완전히 비는 일은 없다.
> 그래서 무엇이 중요한가
> 속도 자체보다 **무엇을 디스크에 두느냐**가 먼저다. 같은 하드디스크로 **전문가 가중치**를 스트리밍하면 토큰당 2.2 GB ÷ ~110 MB/s = **20초/토큰(0.05 tok/s)** 이다. 같은 장치에서 **190배** 차이가 난다. n-gram 테이블은 토큰당 1.9 KB 라 읽기가 임계 아래이기만 하면 사실상 공짜가 된다.

## 04. 세 가지 방식 — 공정하게

셋 다 같은 수학을 한다. 차이는 *테이블을 어느 저장 계층에 두느냐*와, 그 대가다.
먼저 **토큰 하나를 만들 때 각 방식이 어디서 얼마를 끌어오는지**다. 이게 방식을 가르는 근본 수치다.
| 방식 | 테이블 정밀도 | 필요한 데이터 | 실제 전송량 | 초당 |
|---|---|---|---|---|
| 전부 VRAM | 6 bpw | 1.9 KB | — (VRAM 내부) | — |
| FreeToken — pinned RAM | 8 bpw | 2.6 KB | 2.6 KB | 124 KB/s |
| SSD 페이징 | 6 bpw | 1.9 KB | 최대 64 KB | 최대 2.7 MB/s |
| (대조) 전문가를 매번 교체 | — | 2.21 GB | 2.21 GB | 93 GB/s |

맨 아랫줄이 **"왜 보통은 안 되는가"** 다. 전문가 가중치를 저장 계층에 두면 토큰당 2.21 GB 를 끌어와야 하고, 42 tok/s 를 내려면 **초당 93 GB** 가 필요하다. 어떤 저장장치도 못 한다. n-gram 테이블은 **34,000배 적다.**
위 세 줄은 **필요한 데이터가 다 2 KB 안팎으로 같다.** 어느 방식이든 토큰당 16행만 꺼내면 되기 때문이다. 다른 것은 **그 16행이 어디 있느냐**뿐이고, 그래서 전송량도 VRAM 내부냐 · RAM 이냐 · 디스크냐로만 갈린다.
SSD 페이징만 전송량이 데이터보다 **34배** 크다. 필요한 건 1.9 KB 인데 디스크는 **4 KB 페이지 단위로만** 읽으므로, 16행이 서로 다른 페이지에 흩어져 있으면 16번의 읽기가 각각 4 KB 를 가져온다. 캐시가 데워질수록 이 값은 0 을 향해 내려간다 — 64 KB 는 **캐시가 하나도 없을 때의 상한**이다.

### 방식별 비교표

| 축 | 전부 VRAM | FreeToken · vLLM | SSD 페이징 |
|---|---|---|---|
| 테이블의 거처 | GPU VRAM | 호스트 RAM — pinned | NVMe 파일 — mmap |
| 필요 VRAM (4.27bpw 기준) | 54.5 + 38.4 GB | 54.5 GB | 54.5 GB |
| 필요 호스트 RAM | 약 0 | 47.7 GiB 고정 | 0 — 남는 만큼 캐시로 |
| ↳ 정말 0이면? | 해당 없음 | RAM 0 = 캐시 0 = **미스율 100%**. 그때 실측 **41.9 tok/s**. 실제로는 남는 RAM 이 자동으로 캐시가 되므로 항상 이보다 빠르다 |  |
| 디코드 손해 | 없음 (기준) | 없음 | 0 ~ 14% — 미스율에 비례 |
| 콜드 프리필 손해 | 없음 | 없음 | 최대 2.5배 — 30k 프롬프트 첫 처리 시 665 → 262 tok/s |
| 성능의 예측 가능성 | 일정 | 일정 | 흔들림 — 캐시 상태에 따라 41.9 ~ 48.5 tok/s |
| 다른 프로세스의 디스크 부하 | 면역 | 면역 | 취약 — 경쟁 읽기 57k op/s 에서 −25% |
| SSD 쓰기 / 수명 | 해당 없음 | 해당 없음 | 쓰기 0 — 순수 읽기 |
| 메모리 압박이 오면 | 해당 없음 | 버틸 수 없다 — pinned 는 스왑조차 안 된다 | clean page 라 그냥 버린다 |
| 모자랄 때의 모습 | OOM | 안 뜨거나 OOM — 중간이 없다 | 캐시 히트율만큼 **완만하게** |
| 이 박스 64 GiB VRAM · 30 GiB RAM | ✗ 테이블만 95 GiB(BF16) | ✗ RAM 30 GiB < 47.7 GiB | ✓ 41.9 ~ 48.5 tok/s |

> 정직하게
> SSD 페이징은 **공짜가 아니다.** 디코드를 최대 14% 내주고, 처음 보는 긴 프롬프트에서는 프리필이 2.5배 느려지며, 성능이 캐시 상태에 따라 흔들리고, 다른 프로세스가 디스크를 쓰면 같이 느려진다. 전부 VRAM 에 올릴 수 있다면 그게 언제나 낫다.
> 이 방식이 이기는 조건은 하나뿐이다 — **다른 방법으로는 아예 안 뜰 때.** 이 박스가 그렇다. 그리고 그때 **실패가 연속적**이라는 것이 결정적이다: RAM 이 모자라면 히트율이 떨어져 조금 느려질 뿐, 뜨느냐 마느냐가 바뀌지 않는다. FreeToken 의 47.7 GiB pinned 는 커널이 옮길 수도 내보낼 수도 없어서 "느리게라도 도는" 선택지가 아예 없다.
