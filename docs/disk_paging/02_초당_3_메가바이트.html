초록

대형 MoE 모델의 파라미터 중 51.2B(29%)를 메모리에 올리지 않고 NVMe 파일에 남긴 채 추론하는 방식(SSD 페이징)의 비용을 측정했다. 같은 입력을 반복해 디스크 I/O 가 정확히 0인 조건을 만들고 콜드 조건과 대조하는 방법으로 페이징 비용만 분리했다.

결과: 100% 미스에서 디코드는 47.88 → 41.93 tok/s (−12.4%). 프로세스별 major fault 계수로 확인한 폴트는 토큰당 16.21회로 이론값(16행)과 일치했고, 폴트당 정확히 4,096 B를 읽었다(readahead 없음). 폴트 실효비용은 183 µs로 이 장치의 4 KB 랜덤 QD1 실측치(165 µs)에 근접해, 게더가 직렬로 발행됨을 시사한다.

base 계열 세 빌드(본체 46.4 / 55.6 / 55.6 GB)에서는 토큰당 가중치가 18% 늘어도 디코드가 0.4% 빨라졌다 — 대역폭 항(+0.28 ms)과 커널 항(−0.29 ms)이 상쇄되기 때문이다. 반대로 프리필은 같은 빌드에서 1.37배 벌어졌다.

비용의 구조는 고정항 + 폴트수 × 폴트지연 이다. 이 곱 구조를 두 축에서 독립적으로 확인했다. 디스크 경합(경쟁 4 KB 랜덤 읽기 57,458 op/s)은 폴트 지연을 5.4배로 키워 콜드 디코드를 25% 떨어뜨리지만, 폴트가 0인 디코드는 48.16 → 47.85 tok/s 로 무변화다. PLE 테이블 샤드만 2009년식 7200 rpm HDD 로 옮겼을 때도 같다 — 콜드는 41.96 → 9.59 tok/s 로 무너지지만 웜은 48.35 vs 48.80 으로 동일하다. 장치는 폴트가 발생할 때만 보인다.

마지막으로 본체 크기가 0.3% 안에 일치하고 양자화 타입만 다른 두 빌드를 대조했다. 대역폭 항이 0.006 ms 안에 묶였는데 디코드가 15.1% 갈렸다 (47.72 → 54.94 tok/s). 앞선 세 빌드에서 '고정 오버헤드' 처럼 보였던 18.9 ms 는 고정이 아니라 양자화 타입에 따라 변하는 커널 비용이며, 통념과 달리 i-quant 조합이 K-quant 조합보다 빨랐다. 폴트당 비용은 204 vs 216 µs 로 빌드에 무관해, 커널 항과 페이징 항이 독립임이 확인됐다.

이전 판이 합성 QD1 벤치마크로 외삽한 HDD 예측(6.20 tok/s)은 18% 비관적 이었다 — 실측 폴트 지연은 7,280 µs 로 예측(8,780)보다 낫다. 모델의 구조는 맞았고 상수가 어긋났다. 또한 계측 과정에서 히트율 공식 오류, 장치 카운터 오염, 무효한 경합 처치 세 가지 함정을 확인해 정정했다.

2계측을 믿을 수 있게 만들기

페이징 비용만 분리하려면 디스크를 안 건드리는 동일 작업이 있어야 한다. temperature=0, top_k=1, seed=42 로 같은 프롬프트를 반복하면 출력 토큰열이 바이트 단위로 같으므로 정확히 같은 n-gram 행만 건드린다. 1회차는 콜드, 2회차부터는 그 행들이 페이지 캐시에 있다. 차이가 곧 페이징 비용이다.

함정 1 — 장치 단위 카운터는 오염된다

/sys/block/nvme0n1/stat 은 장치 전체를 센다. 1차 측정에서 요청당 3~5 GB 라는 불가능한 값이 나왔는데, 원인은 같은 NVMe 에서 다른 모델을 받고 sha256 을 검증하던 다운로더였다(누적 84 GB 읽기). 프로세스별 /proc/<pid>/io 의 read_bytes 로 바꾸자 값이 안정됐다.

함정 2 — 히트율 공식이 틀려 있었다

기존 계획서는 히트율 = 1 − 읽은바이트 ÷ (N × 2764) 였다. 이는 I/O 바이트를 데이터 바이트로 나눈다. 게더는 4 KB 페이지 단위로 일어나므로 100% 미스일 때의 I/O 는 2,764 B 가 아니라 65,536 B 다. 옛 공식은 히트율을 음수로 만든다.

정정된 공식 — 히트율 = 1 − (major fault 수) ÷ (토큰수 × 16). 분자를 바이트가 아니라 폴트 수로 세는 것이 핵심이다. /proc/<pid>/stat 의 maj_flt 로 직접 얻는다.

3.1 페이징 비용의 분리

세 가지가 한꺼번에 확정된다.

  1. 웜 조건에서 디스크 I/O 가 문자 그대로 0이다. 읽기 0 바이트, major fault 0회. 이것이 "테이블이 RAM 에 있을 때"의 상한선이다 — 47.88 tok/s.
  2. 콜드에서 토큰당 16.21 폴트는 이론값 16행과 일치한다. 16개 행이 서로 다른 페이지에 흩어져 있다는 뜻이고, 표 1 의 I/O 상한 모델이 맞다는 확인이다. (초과분 0.21 은 프롬프트 20토큰의 프리필 몫이다.)
  3. 폴트당 4,393 B ≈ 4,096 B. 커널이 폴트 하나에 페이지 하나만 읽는다 — fault-around 나 readahead 가 걸리지 않았다. 랜덤 게더에 정확히 맞는 동작이다.
폴트 실효비용 = 2.97 ms ÷ 16.21 = 183 µs. 이 장치의 4 KB 랜덤 QD1 실측 지연은 165 µs 다. 둘이 근접한다는 것은 16개 폴트가 겹치지 않고 직렬로 발행된다는 뜻이다 — 큐 깊이 1. 게더를 병렬로 던질 수 있다면 여기에 개선 여지가 남아 있다.

서로 겹치지 않는 신규 텍스트 18종으로 미스율을 흩뜨렸다. 프리필에서도 토큰당 16행 게더가 일어나므로 미스율은 (프리필 + 디코드) 토큰 기준이다.

구간 평균이 단조롭지 않다(46.46 → 43.92 → 44.19). 회귀도 토큰시간(ms) = 21.18 + 0.048 × 폴트/토큰, R² = 0.21 이다.

이 설계에는 노이즈보다 큰 결함이 있다 — 부분적 오설정이다. 폴트의 대부분은 프리필에서 발생하는데(프롬프트 ~600토큰 × 16행), predicted_per_second 는 디코드 시간만 잰다. x축과 y축을 서로 다른 토큰 집단에서 측정하고 있었다. §3.4 이후의 실험은 프로토콜을 바꿨다 — 짧은 고정 프롬프트(프리필 폴트를 전체의 7%로 억제) + 매 런 다른 seed (생성 토큰열이 매번 새것이라 디코드 미스가 유지된다) + ignore_eos(길이 고정).

따라서 이 절의 회귀는 참고용이고, 폴트 비용의 신뢰할 만한 값은 통제된 §3.1(183 µs)과 §3.4·§4 의 짝지은 측정에서 나온다. 통제된 F1 실험(183 µs)이 더 신뢰할 만한 값이고, 회귀의 절편 21.18 ms(= 47.2 tok/s)가 F1 의 웜 값 20.89 ms(47.88 tok/s)와 일치한다는 점이 두 실험이 같은 것을 재고 있다는 교차 확인이다.

3.4 디스크 경합 — 1차 실험은 무효였다

4.2 장치 종류가 따로 작용하는가 — 아니다

앞 절은 NVMe 와 HDD 를 비교했다. 그런데 두 장치는 지연 말고도 여러 가지가 다르다 (탐색 유무, 큐 구조, 전송 속도). 지연이 충분통계인지 — 즉 지연만 같으면 장치 종류는 무관한지 — 를 가리려면 같은 장치를 느리게 만들어 비교해야 한다.

같은 NVMe 에 경쟁 4 KB 랜덤 읽기 부하를 걸어 폴트 지연만 올렸다. 하드디스크가 느린 원인 (헤드 이동)과는 전혀 다른 원인이다.

4.7 미스율 0 근처 — 평균은 매끄럽고 분포는 계단이다

"1바이트만 읽어도 디스크 지연은 온전히 낸다" 는 것은 사실이고, 그 고정비용은 이미 L 안에 있다 — L = 209 µs 는 전송 시간이 아니라 접근 한 번의 총비용이고, 전송분은 2.6 µs(1.2%)뿐이다(표 2). 그래서 미스율 → 0 에서 수직 점프는 생기지 않는다. x축이 접근 횟수의 비율이기 때문이다: 미스율 0.0001% 는 "1바이트를 읽는다" 가 아니라 "62,500 토큰당 한 번 209 µs 를 낸다" 이고, 토큰당 평균으로는 0.0000033 ms 다.

다만 분포는 다르다. 낮은 미스율에서 토큰 시간은 이봉분포가 된다 — 대부분의 토큰이 20.6 ms, 드문 토큰이 20.6 + 0.209 ms. 평균은 연속이지만 개별 토큰은 계단이다. 이 보고서는 처리량만 다루므로 그 효과가 드러나지 않는다. 지연 백분위수(p99 등)를 볼 때는 별도 측정이 필요하다 — 미측정 항목이다(§10).

7.2 imatrix 가 여기서 만나는 지점

importance matrix 는 실제 모델을 코퍼스에 돌려 각 입력 열이 어떤 크기의 활성값과 곱해지는지를 누적한 표다. 양자화의 목적함수를 Σ(w−ŵ)² 에서 Σ importance·(w−ŵ)² 로 바꾼다. 런타임 비용은 0이고 파일 안의 숫자만 달라진다. 그런데 —

PLE 테이블은 imatrix 를 받을 수 없다. llama-imatrix 는 MUL_MAT 과 MUL_MAT_ID 만 수집하고 나머지 연산은 건너뛴다 (tools/imatrix/imatrix.cpp:246-247). GET_ROWS 인 이 텐서는 코퍼스를 아무리 키워도 통계가 0개다. 51.2B 가 영구히 눈감고 양자화된다.

dense 모델에는 이 수법을 쓸 수 없다. 정의상 모든 가중치가 매 토큰 쓰이므로, 일부만 디스크에 둬도 그 일부를 토큰마다 통째로 읽어야 한다. 8 GB 만 밖에 둬도 토큰당 5초다. dense 모델은 전부 VRAM 에 들어가야 하고, 그때의 속도는 대역폭이 정한다 — 이 카드에서 64 GB 를 채우면 이론 상한이 25 tok/s 다 (64 GB ÷ 1,592.8 GB/s = 40.2 ms/토큰).

dense 모델에도 색인 텐서는 있다. token_embd 는 토큰 ID 로 한 행만 뽑는 GET_ROWS 라 조건을 만족한다. 다만 어휘 150k × hidden 5,120 이면 BF16 으로 1.5 GB 남짓이라 64 GB 예산에서 빼봐야 실익이 없고, 출력 헤드는 행렬곱이라(매 토큰 전체 어휘에 대해 로짓을 낸다) 애초에 대상이 아니다. 가중치가 묶여 있으면 분리조차 안 된다.

표 36 — 철회·정정 목록
#처음 믿은 것실제어떻게 드러났나
1"SSD 페이징은 디스크 경합에 견고하다" 근거 없음 — 처치가 무효였다 '경합' 이 모델 다운로드였다. 인터넷에 묶인 62 MB/s 쓰기로, 폴트가 다투는 4 KB 랜덤 읽기 IOPS 를 건드리지 않았다. 진짜 부하로 재자 −25% (§4.1)
